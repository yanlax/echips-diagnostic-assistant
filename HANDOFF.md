# Передача сессии — Echips Hardware Check

Последняя выпущенная версия: **v0.10.0** (тег и релиз на GitHub). Поверх
неё в этой сессии сделаны ещё две доработки (см. ниже), которые пока
**не оформлены как релиз** — ждут проверки пользователем на реальном
железе, прежде чем поднимать версию.

## Что сделано в версиях v0.8.0 → v0.10.0 (см. git log/README.md по датам)

Коротко, подробности — в README.md и коммитах:
- PDF-экспорт отчёта (printpdf 0.7, шрифт PT Sans).
- Автопрогон: интерактивные тесты первыми в очереди.
- Тест «Драйверы» в диагностике/автопрогоне (только проверка, без установки).
- Активация Windows: автоустранение при провале (синхронизация времени →
  перезапуск службы → онлайн-активация → OEM-ключ).
- Стресс-тест: убран ложный троттлинг (нужна ещё и просадка частоты CPU,
  не только Мопс/с).
- Wi-Fi: `Get-NetAdapter -Physical`, чтобы не ловить виртуальные адаптеры.
- Диск: поверхность красится по доле пройденного диапазона, а не по
  абсолютной позиции.
- Журнал сбоев: честная формулировка про Kernel-Power 41 (не отличает
  потерю питания от удержания кнопки).
- Память: тестовый объём вернули на 4 ГБ (было экспериментально 16 ГБ —
  слишком долго для рутинного автопрогона), добавлено ETA "осталось ~N с".
- Поле «Общий комментарий инженера» на экране отчёта — уходит в
  `summary_comment` во всех форматах экспорта.
- Экспорт TXT/JSON/PDF теперь сам открывает папку с сохранённым файлом
  (`open_containing_folder`). Порядок кнопок — JSON/TXT/PDF (PDF главный,
  справа).
- Переключатель темы (light/dark) — сначала в титлбаре, затем (после
  правки ниже) в сайдбаре.
- PDF v1: сплошной тёмный фон, фирменный логотип, построчный текст по
  тестам (без карточек) — вышло в v0.10.0.

## Эта сессия: разбор реального PDF-отчёта + 3 плана доработок

Пользователь прислал реальный экспортированный PDF (v0.10.0) с пометками
техника и три файла для сравнения дизайна: реальный PDF, референс-превью
PDF и **референс-шаблон `echips_report_template.html`** (полноценный
CSS-дизайн: светлая «бумага», тёмная обложка сверху с лого/заголовком/
метаданными/вердикт-пилюлей/чипами, карточки тестов с цветной полосой
слева и бейджем статуса). Из пометок и прямых пожеланий вышло три пункта:

### 1. Переключатель темы перекрывал кнопки экранов — ИСПРАВЛЕНО

Пилюля темы была реализована как в `echips-driver-assistant`:
`position:absolute` поверх `.content`, в правом верхнем углу — там же, где
у многих экранов `.headactions` (кнопки «Автопрогон», «К отчёту» и т.п.).
Перенесена в статичный слот в левом сайдбаре, под блоком устройства, над
подвалом «© Echips»:
- `src/index.html` — `<div class="theme-toggle-slot" id="theme-toggle-slot">`
  между `.devbox` и `.sidefoot`.
- `src/theme.js` — `mount()` ищет `#theme-toggle-slot` вместо `.content`.
- `src/style.css` — `.theme-toggle` из floating/blur в статичную пилюлю,
  добавлен `.theme-toggle-slot`.

Проверено браузерным стендом (скриншоты) — пилюля больше ничего не
перекрывает. **Закоммичено и запушено**, войдёт в следующий релиз.

### 2. PDF-отчёт — полная переверстка под референс-дизайн

`src-tauri/src/commands/report.rs`: старый сплошной тёмный `render_pdf()`
(v0.10.0) заменён на светлую «бумагу» с тёмной обложкой сверху (по
референсу):
- Обложка (тёмная плашка ~72–78мм на первой странице): лого, заголовок
  «Отчёт диагностики», подзаголовок, 3-колоночная метасетка (устройство /
  серийник / начало+длительность), вердикт-пилюля («Неисправностей не
  выявлено» / «Выявлено неисправностей: N»), три счётчика-чипа.
- Блок комментария инженера — светлый фон + оранжевая полоса слева
  (если `summary_comment` не пуст).
- Сводная строка из трёх цветных чипов (пройдено / вне профиля-не
  проверено / неисправно) — статусы объединены в 3 «ведра» как в
  референсе (`bucket_of`/`bucket_colors`).
- Каждый тест — отдельная карточка: рамка, цветная полоса слева по
  статусу, бейдж статуса в правом верхнем углу, заголовок, краткое
  описание, при наличии — строка про смену автовердикта и подробности.
- Итоговый блок — цветная плашка с вердиктом и списком неисправностей.

**Архитектурная деталь** (важно при следующей правке): PDF рисуется
строго аддитивно, слой за слоем — нельзя нарисовать что-то «под» уже
нарисованным текстом. Высота карточки заранее не известна (зависит от
переноса строк), поэтому `draw_card()`:
1. Сначала «примеряет» высоту через те же `wrap_line()`/`max_chars_width()`,
   что при реальной отрисовке — решает, стоит ли начать новую страницу.
2. Рисует бейдж (фиксированная позиция сверху), затем текст сверху вниз.
3. **Рамку и цветную полосу слева рисует последними**, поверх уже
   готового содержимого — но только в местах, которые текст не занимает
   (гуттер слева до текста, периметр карточки), поэтому ничего не
   перекрывает.
4. Если карточка разорвалась между страницами (`w.page_no` изменился) —
   рамка не рисуется вовсе (обрамляла бы только часть содержимого).

**Сознательные упрощения** относительно референса (см. комментарий в
начале PDF-секции `report.rs`): прямые углы вместо скруглённых, один
плоский список строк в карточке вместо двухколоночной kv-сетки/таблицы
журнала/плашки диагноза — под точную структуру пришлось бы менять
модель данных, которую `recordDetail()` шлёт из **всех** тестов в
`app.js` (сейчас `details: Vec<String>`, а не структурированные пары).
Это отдельная, более крупная задача — если пользователь после проверки
захочет точное совпадение, браться за неё отдельно.

Проверено только `cargo check --lib` на macOS (компилируется чисто, без
новых предупреждений) — **реальный рендер PDF не воспроизвести
локально**, нужен новый прогон и свежий экспорт от пользователя для
визуальной сверки с референсом. Закоммичено и запушено
(`e5e7466`), в релиз ещё не оформлено.

### 3. Блокировка Win-клавиши не останавливала «Пуск» — доработано, НЕ ПРОВЕРЕНО

Реальный тест на железе (комментарий техника в PDF) показал: клавиша Win
всё равно открывала меню «Пуск» (блокировка срабатывала только на
последующих нажатиях, уже открытое меню закрыть тоже не получалось).
Также попросили заблокировать «F-ряд и все клавиши, которые
взаимодействуют с Windows».

`src-tauri/src/commands/keyhook.rs` доработан:
- Список «съедаемых» кодов клавиш расширен с Win до медиа-клавиш
  (громкость/мьют, медиаплеер, браузер, лаунчер) — на части ноутбуков
  именно они всплывают системным OSD и мешают технику видеть, сработала
  ли клавиша. Яркость туда сознательно не входит — как и Fn, у неё нет
  отдельного VK-кода, обрабатывается контроллером/BIOS до ОС.
- Добавлена вторая линия защиты: пока блок включён, слушаем
  `EVENT_SYSTEM_FOREGROUND` через `SetWinEventHook` — если, несмотря на
  перехват клавиши, активным окном всё же стал Start UI (проверяем ОБА
  признака: класс окна `Windows.UI.Core.CoreWindow` И имя процесса
  `StartMenuExperienceHost.exe`/`ShellExperienceHost.exe`, чтобы не
  закрыть что-то другое с тем же классом окна — например поиск или
  центр уведомлений), сразу шлём ему Escape через `SendInput`.

Это гипотеза, основанная на разборе документации Win32 API (не на
эксперименте) — **не гарантирует полное решение проблемы**. Возможная
причина, почему один только `WH_KEYBOARD_LL` не сработал: открытие
«Пуска» по одиночному тапу Win может обрабатываться системой на более
низком уровне (raw input), чем обычный хук клавиатуры — тогда `SendInput
Escape`-подстраховка должна закрыть уже открывшееся меню почти
мгновенно, даже если сам хук не успел его предотвратить.

Проверено только: скачан исходник `windows-sys 0.59.0` из
`~/.cargo/registry` и вручную сверены все сигнатуры функций/типы полей
структур (`SendInput`, `SetWinEventHook`, `GetWindowThreadProcessId`,
`QueryFullProcessImageNameW`, `INPUT`/`KEYBDINPUT`, коды `VK_*`) — раз
`cargo check --lib` на macOS этот код вообще не собирает (весь модуль
под `#[cfg(target_os = "windows")]`). **Запущена сборка через GitHub
Actions** (`gh workflow run build.yml`, ID см. `gh run list`) — это
проверяет только компиляцию на Windows, НЕ фактическое поведение.
**Обязательно нужен реальный тест техником** на железе прежде чем
считать пункт закрытым — если Escape-подстраховка тоже не поможет,
следующая гипотеза (не реализована) — переустанавливать хук при каждом
получении фокуса экраном теста клавиатуры, на случай если explorer.exe
на старте теста перехватывает хук-цепочку позже нашего хука.

Закоммичено и запушено (`f9f6241`), в релиз ещё не оформлено.

## Принятые решения и почему

- **PawnIO вшивается и ставится автоматически без диалога** — осознанное
  решение пользователя.
- **LibreHardwareMonitor вместо ACPI/WMI** для температур/вентиляторов.
- **Троттлинг в стресс-тесте требует падения частоты CPU**, не только
  просадки Мопс/с/ГФлопс.
- **Профили моделей — один `default` на все**, пока не попросят иначе.
- **Активация Windows: автоустранение без подтверждения на каждый шаг.**
- **Автовердикт нельзя менять без причины в комментарии**, и **нельзя
  ставить вердикт, пока тест ещё выполняется.**
- **Обходы активации Windows и подбор AMIDEWINx64 флагов из интернета —
  отказ.**
- **PDF-статусные цвета взяты из референс-шаблона пользователя**
  (`echips_report_template.html`), а не из тёмной темы интерфейса —
  так пожелал пользователь после проверки первой (полностью тёмной) версии.
- **Карточки PDF — плоский список строк, не точная kv-сетка/таблица
  референса** — сознательное упрощение, чтобы не менять модель данных
  `recordDetail()` во всех тестах ради одной верстки; можно углубить
  отдельной задачей, если после визуальной проверки понадобится.

## Известные баги (открытые)

- **Блокировка Win/медиа-клавиш на тесте клавиатуры не подтверждена на
  реальном железе** — см. пункт 3 выше, требует нового теста.
- **PDF-переверстка не подтверждена визуально** — требует нового
  экспорта от пользователя, см. пункт 2 выше.
- Разбор минидампа для виновного модуля не реализован — нужен образец
  `.dmp`.
- SMART-объём записи/чтения для части SSD может быть неверной единицей
  (эвристически скрывается, если < 1 ГБ при >200ч наработки).
- Автоопределение вентиляторов зависит от поддержки контроллера EC в
  LibreHardwareMonitor — на части ноутбуков не находятся, это не баг.
- `Kernel-Power 41` не отличает реальную потерю питания от удержания
  кнопки техником — ограничение источника данных Windows.
- Клавиша Fn и яркость экрана не видны системе (обрабатываются
  контроллером/BIOS до ОС) — не баг, программно не решается.

## Что нельзя трогать без явного запроса/данных

- `tauri.conf.json` / `capabilities/default.json` (права и
  `withGlobalTauri` уже настроены).
- `write_smbios_identity` — не подставлять команды из интернета.
- Пин SHA-256 установщика PawnIO в `.github/workflows/build.yml`.
- Автоустановка PawnIO без диалога — оставлять как есть.
- Не пытаться собирать Rust-код с `#[cfg(target_os = "windows")]` как
  доказательство корректности — `cargo check --lib` на macOS такой код
  вообще не видит (условная компиляция вырезает), нужна сборка CI на
  Windows + реальный тест на железе. `cargo check --lib` на macOS при
  этом РЕАЛЬНО РАБОТАЕТ для платформо-независимого Rust-кода (вопреки
  более старой заметке в CLAUDE.md) — этим стоит пользоваться для
  быстрой проверки перед пушем, но он не заменяет CI/реальный тест для
  Windows-специфичного кода.
