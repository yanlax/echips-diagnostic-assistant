# Echips Hardware Check

Tauri 2 приложение для инженеров сервисного центра Echips: аппаратная
диагностика ноутбука, установка драйверов (тот же каталог/механизм, что и в
`echips-driver-assistant`) и процедура замены материнской платы с
журналированием.

Дизайн — из присланного прототипа `diag.zip` (тёмная тема, оранжевый акцент,
шрифты Space Grotesk/Inter/JetBrains Mono), перенесён 1-в-1 по вёрстке.
Отличие от прототипа: там, где в макете были случайные/симулированные данные
(графики температуры, прогресс-бары на `setInterval`, фейковые списки
устройств) — здесь везде реальные вызовы Rust-команд или браузерных API. Где
честного способа получить данные без стороннего софта нет — сделан явный
"недоступно", а не подделка.

## Что реально работает (не заглушка)

- **Устройство**: модель, производитель, серийный номер, версия BIOS, ОС,
  CPU, объём ОЗУ — WMI (`Win32_ComputerSystem`/`Win32_BIOS`/`Win32_OperatingSystem`/`Win32_Processor`).
- **Батарея**: текущий заряд/статус зарядки (WMI) + design capacity, full
  charge capacity, health% и счётчик циклов — парсинг XML-отчёта
  `powercfg /batteryreport`.
- **USB / Bluetooth**: список подключённых устройств и их статус через
  `Get-PnpDevice`.
- **Wi-Fi**: список адаптеров (имя/статус/MAC, только физические — `-Physical`
  отсекает виртуальные Wi-Fi Direct адаптеры, которые почти всегда «Not
  Present» и раньше ложно роняли тест) + список видимых сетей через
  `netsh wlan show networks`.
- **Отпечаток пальца**: определение наличия биометрического сенсора в
  системе (класс `Biometric` в PnP).
- **Камера**: живое превью через `navigator.mediaDevices.getUserMedia()`.
- **Звук**: генерация тона и визуализация спектра через Web Audio API
  (`AudioContext`/`OscillatorNode`/`AnalyserNode`), эхо-тест микрофона.
- **Автопрогон и профили моделей**: режим «Автопрогон» последовательно
  гоняет тесты по профилю модели (`src/profiles.js`). Автоматические
  проверки (системная информация, диск, журнал сбоев, USB, Bluetooth,
  Wi-Fi, LAN, отпечаток, батарея, а также SMART, чтение, запись и
  поверхность диска, память и датчики; стресс-тест в автопрогон не входит,
  но добавляется в `tests` профиля) сами запускаются, ставят вердикт по порогам
  профиля и идут дальше (длительность стресс-теста, объём памяти, размер
  файла записи и пороги температуры — в профиле);
  интерактивные (клавиатура, матрица, камера, тачпад, звук) ждут отметки
  техника. Профиль: порядок тестов, `stopAtFail`, порог здоровья батареи
  (по умолчанию 80%), `required` (что обязательно на ноутбуке), эталон
  железа `expect` (CPU, ОЗУ, диск, BIOS). Профиль модели накладывается на
  `default` по вхождению кода модели. На настольном ПК отсутствие
  батареи/Wi-Fi/Bluetooth = «не применимо», на ноутбуке из `required` —
  неисправность. Примеры профилей — в комментарии внутри `profiles.js`;
  реальные эталоны по моделям Echips нужно внести.
- **Системная информация**: процессор, модули ОЗУ (слот, объём, частота,
  производитель), диски (модель, объём, тип, здоровье), видеокарта,
  плата, BIOS, тип корпуса — из WMI, со сверкой с `expect` профиля.
- **Диск: здоровье**: состояние, износ, температура, часы, неисправленные
  ошибки (Get-PhysicalDisk + счётчики надёжности) с автовердиктом по
  `diskMaxWearPct` профиля.
- **Журнал сбоев — уточнения по реальным отчётам**: исправленные ошибки WHEA
  (обычно PCIe AER) считаются отдельно от критичных и дают лишь справку;
  номер диска в событиях (`\\Device\\Harddisk2\\DR2`) заменяется его именем;
  на настольном ПК формулировки про питание без батареи/зарядки.
- **Активация Windows**: статус лицензии (`SoftwareLicensingProduct`), канал
  (OEM/Retail/Volume), код причины, наличие OEM-ключа в BIOS; автовердикт
  в автопрогоне. При провале активации приложение **само** без лишних
  кликов пробует штатные шаги по очереди — синхронизация времени →
  перезапуск службы лицензирования → онлайн-активация → (если в BIOS есть
  OEM-ключ) его установка, останавливаясь сразу при успехе; лог каждого
  шага виден в подробностях теста. Ввод стороннего ключа — по-прежнему
  только вручную (нужны данные от техника). Если автоматика не помогла,
  под тестом остаются те же кнопки для ручного разбора (в т.ч. свой ключ,
  страница активации Windows). Только штатные механизмы через WMI; обходов
  активации (KMS-эмуляторы и т. п.) в приложении нет и не будет. Ключи не
  попадают в `perf.log`.
- **Драйверы (проверка)**: в диагностике и автопрогоне отдельным тестом —
  устройства с ошибкой в Диспетчере устройств (`list_problem_devices`).
  Только показывает список и предлагает поставить их во вкладке
  «Установка драйверов» — сам ничего не ставит.
- **Журнал сбоев** (дополнение): записи трёх источников склеиваются в один
  сбой (окно 2 минуты: дамп, событие WER, Kernel-Power), справочник
  расширен (~70 кодов, вариант с флагом `0x1000007E → 0x7E`), показаны
  параметры остановки, аппаратные события (WHEA, ошибки диска, TDR) и
  диагноз по шаблону: разные коды подряд, коды ОЗУ/диска/видео, внезапные
  отключения, регулярный интервал, повторяющийся код; под диагнозом —
  кнопки рекомендуемых тестов. Виновный модуль из дампа пока не
  определяется (нужен образец дампа для проверки разбора).
- **Журнал сбоев**: события WER 1001 / Kernel-Power 41 и файлы
  `C:\Windows\Minidump` (код остановки читается из заголовка дампа),
  расшифровка кода и вероятная причина; вердикт по окну `crashDays`.
  Виновный драйвер без символов Microsoft не определяется.
- **Диск: чтение**: чтение 24 участков физического диска с замером скорости,
  медленными блоками (>250 мс) и ошибками чтения; запись не выполняется.
  Нужны права администратора.
- **Быстродействие**: все Rust-команды выполняются вне главного потока
  (`#[tauri::command(async)]`), окно не замирает на время запросов;
  PowerShell работает постоянным процессом (пул из двух, скрипты по
  stdin в base64) с автоматическим откатом на «процесс на вызов» при любой
  проблеме (`ECHIPS_PS_HOST=0` отключает); таймаут вызова 120 с; дорогие
  запросы (диски, сводка железа) кэшируются в автопрогоне; тест памяти
  оставляет одно ядро интерфейсу и работает с пониженным приоритетом.
  Время каждого вызова пишется в `%LOCALAPPDATA%\Echips\HardwareCheck\perf.log`
  — по нему находят узкие места на бюджетных моделях.
- **Отчёт с подробностями**: строки отчёта кликабельны — открывается экран
  теста с логом, автооценкой, графиком скорости (диск) и причиной, если
  техник изменил автовердикт. Изменить автовердикт можно только с
  причиной в комментарии. Подробности попадают в TXT/JSON/PDF. Тесты вне
  профиля помечаются «вне профиля», а не «не проверено». На самом экране
  «Отчёт» есть поле «Общий комментарий инженера» (не привязан к
  конкретному тесту) — тоже попадает во все три формата экспорта.
- **Экспорт PDF**: рядом с TXT/JSON — тот же состав данных, свёрстанный
  на A4 (шрифт PT Sans, кириллица, вшит в exe из `src-tauri/assets/fonts`).
  Перенос строк — по эвристике «средний символ ≈ 0.52 кегля» (метрики
  шрифта printpdf 0.7 наружу не отдаёт), для служебного отчёта точной
  вёрстки не требуется. После экспорта (TXT/JSON/PDF) сразу открывается
  Проводник с подсвеченным файлом (`explorer /select,...`). Тёмный фон и
  цвета — как в интерфейсе приложения (см. `palette()` в `report.rs`,
  значения взяты из `:root` в `src/style.css`): фирменная шапка на первой
  странице (логотип `src-tauri/assets/logo.png`, оранжевая линия под ней),
  заголовки разделов и статусы pass/fail в тех же цветах, что и в самом
  приложении; на страницах со 2-й — тонкий футер снизу с названием и
  серийником. На экране «Отчёт» кнопка PDF — основная (справа, оранжевая),
  TXT/JSON — вспомогательные.
- **Окно**: кнопка «Развернуть/восстановить», двойной клик по заголовку и
  F11 — полноэкранный режим; заливка матрицы не сбрасывает полноэкранный
  режим техника.
- **Тема интерфейса**: тёмная/светлая, тот же визуальный паттерн, что в
  `echips-driver-assistant` — пилюля с двумя кнопками (луна/солнце), а не
  один тумблер; размещена в левом сайдбаре снизу, над «© Echips»
  (`#theme-toggle-slot` в `index.html`) — изначально пробовали поверх
  рабочей области в правом верхнем углу, но там она перекрывала кнопки
  экранов вроде «Автопрогон»/«К отчёту» (замечание по реальному отчёту).
  `src/theme.js` монтирует один раз, не зависит от перерисовок `#screen`;
  атрибут `data-theme` на `<html>`, выбор в `localStorage`.
  Светлая тема — та же CSS-переменная для акцента (`#FF8A00`), только
  инвертирована яркость фона/текста в `[data-theme="light"]`
  (`style.css`); по умолчанию — тёмная. `#screen` теперь вложен в
  `.content` (класс `.screen`) специально под это — раньше это был один
  и тот же элемент.
- **Клавиатура**: цифровой блок, счётчик нажатий ×N на каждой клавише,
  дребезг (два срабатывания быстрее 25 мс), залипание (нажата >3 с),
  ряд мультимедиа-клавиш для проверки Fn-комбинаций. Кнопка «Заблокировать
  Win на время теста» — низкоуровневый системный хук клавиатуры
  (`WH_KEYBOARD_LL`, `commands/keyhook.rs`, крейт `windows-sys` — здесь
  единственное место в проекте с прямым WinAPI вместо PowerShell): Win
  иначе открывает меню «Пуск» и мешает проверке, а обычный
  `preventDefault()` в JS системные хоткеи не останавливает. Включается
  только вручную; снимается при выходе с экрана теста и при закрытии
  приложения — на случай, если техник забудет выключить сам.
- **Вкладка «Диск»**: здоровье, SMART, чтение, поверхность и запись собраны
  в одну карточку с подвкладками (`GROUPS` в `app.js`, поле `group` у
  категорий). В автопрогоне и в отчёте каждый тест остаётся отдельным
  шагом/строкой.
- **Диск: SMART** (как CrystalDiskInfo/Victoria): для SATA — таблица
  атрибутов (ID, имя, текущее/худшее/порог, raw), для NVMe — лог здоровья
  (резерв, износ, ошибки целостности, небезопасные выключения, записано
  и прочитано). Итог «Хорошее / Тревога / Плохое» и остаток ресурса, %.
  SATA берётся из WMI (`MSStorageDriver_*`), NVMe — прямым запросом
  `IOCTL_STORAGE_QUERY_PROPERTY`; для USB-переходников и RAID показываются
  базовые счётчики Windows. В автопрогоне «Тревога» считается ошибкой
  (`smartCautionIsFail`). Разбор проверен юнит-тестами, реальные диски —
  только на железе.
- **Диск: поверхность** (как «Read» в Victoria): чтение диска или диапазона
  (весь диск, первые 100/10 ГБ, последние 10 ГБ) блоками по 512 КБ с
  замером времени каждого блока, график скорости в реальном времени
  (ось — доля пройденного диапазона, а не абсолютная позиция на диске:
  при сканировании части диска график раньше оставался почти пустым,
  начало/конец полосы не совпадали с началом/концом самого теста),
  счётчики классов задержки (<5, <20, <50, <150, <500, ≥500 мс, ошибка),
  живые мин/макс скорости во время сканирования и список нечитаемых
  блоков. Только чтение: данные не меняются, диск не изнашивается.
  В автопрогоне — первые `surfaceScanGb` ГБ.
- **Диск: запись**: запись проверочного файла на выбранный том (512 МБ или
  2 ГБ) в обход кэша Windows, чтение обратно с проверкой данных, скорость
  по участкам, медленные блоки. Физический диск не перезаписывается,
  файл удаляется после теста; на системном томе пишется в `%TEMP%`.
  Размеры до 100 ГБ и «максимум» (85% свободного места), график скорости
  записи в реальном времени. Запись 100 ГБ — около 0,03% ресурса SSD на
  300 ТБ, диск это не убивает. Перезапись самих секторов (как «Write» в
  Victoria) не реализована сознательно: она стирает данные, а Windows и так
  блокирует её на смонтированных и системных дисках.
- **Память**: многопоточная запись/проверка паттернов (нули, единицы,
  шахматка, бегущая единица, адрес, случайные), блок не больше 75%
  свободной ОЗУ (и жёсткий потолок 16 ГБ) — остальное намеренно не
  трогается, чтобы не уронить систему во время теста. В автопрогоне по
  умолчанию — 4 ГБ (пробовали поднять до 16 ГБ, но полный объём занимал
  слишком много времени для рутинной проверки — 79 с вместо ~20); во время
  теста видно примерное время до конца, а в отчёте — сколько протестировано
  от установленного объёма ОЗУ. Быстрая проверка на явный брак, не замена
  memtest на загрузочной флешке.
- **LAN**: Ethernet-адаптер, линк и скорость (`Get-NetAdapter`); без кабеля —
  «линк не проверен».
- **Накопитель USB**: обнаружение флешки/USB-диска, запись и чтение
  временного файла в обход кэша Windows (`NO_BUFFERING`/`WRITE_THROUGH`)
  с проверкой данных и реальной скоростью порта; системный диск не
  трогается. Для проверки нескольких портов вставляйте флешку по очереди.
- **Яркость**: ползунок подсветки через WMI (ноутбуки); на десктопе и
  внешних мониторах — «не применимо».
- **Внешний монитор**: список мониторов и тип выхода (HDMI/DP/VGA).
  Вывод картинки на второй монитор пока не реализован.
- **Wi-Fi**: уровень сигнала по сетям (`netsh wlan show networks
  mode=bssid`) и порог `wifiMinSignal` профиля — слабый сигнал у роутера
  указывает на антенну/шлейф.
- **Матрица**: 9 цветов из SFT + градиенты, цветные полосы, шахматка,
  сетка, полосы в 1 пиксель (по мотивам TFT TEST).
- **Камера**: запись 5 секунд и воспроизведение.
- **Датчики LibreHardwareMonitor**: в exe вшиты вспомогательный процесс
  `echips-sensors.exe` (LibreHardwareMonitorLib 0.9.6, .NET Framework 4.7.2 —
  есть в Windows 10/11) и установщик драйвера PawnIO 2.2.0. Драйвер
  ставится сам при первом запуске, без вопросов (`-install -silent`); на
  вкладке «Датчики» его можно удалить (тогда автоустановка отключается) и
  поставить снова; после установки датчики запускаются сами и показывают температуры CPU/GPU, обороты вентиляторов,
  напряжения, мощность и частоты. Эти данные автоматически идут в
  стресс-тест (температура, вентилятор, мощность CPU) и в тест «Датчики»;
  без драйвера остаётся ACPI/nvidia-smi. Вложения подготавливает CI
  (`helper/EchipsSensors` → `src-tauri/helper/sensors.zip`, установщик
  пинится по SHA-256); локальная сборка без них собирается с пустыми
  заглушками. См. `THIRD-PARTY-NOTICES.md`.
- **Вентиляторы** (как в SpeedFan): таблица вентиляторов из датчиков
  LibreHardwareMonitor — обороты вживую, min/max за сеанс, ползунок ручной
  скорости 20–100% для управляемых. «Проверка отклика» по очереди задаёт
  100% и 35% и сравнивает обороты (не раскручивается или не реагирует —
  «не пройден»); «пассивная проверка» только читает обороты (вентилятор
  стоит при CPU ≥ 65 °C — «не пройден», в простое 0 об/мин — норма).
  Защита: минимум 20%, ручная скорость сама возвращается в авторежим через
  40 с без обновления, при выходе с экрана и при закрытии приложения;
  вспомогательный процесс отпускает вентиляторы и при обрыве связи. В
  автопрогоне — пассивная проверка (тест `fans`). Работает, если
  LibreHardwareMonitor поддерживает контроллер вентиляторов платы.
- **Датчики** (базовые): ACPI-температура через WMI (на многих платах, включая
  десктопные AMD, её нет) и GPU NVIDIA через `nvidia-smi` (температура,
  вентилятор, мощность, загрузка). Для CPU/вентиляторов без ACPI нужен
  LibreHardwareMonitor — не интегрирован, решение за владельцем проекта.
- **Стресс-тест** (как AIDA64 System Stability Test): выбираемые виды
  нагрузки — CPU (целочисленная), FPU (AVX2/FMA, если есть — самая горячая),
  кэш (наборы под L1/L2/L3), память (запись/проверка паттернов с подсчётом
  ошибок), диск (цикл записи/чтения с проверкой в %TEMP%) и GPU (тяжёлый
  шейдер WebGL прямо в окне). Пресеты: быстрый 1 мин, стандарт 10 мин,
  прогрев до остановки, всё сразу 30 мин; потоки: все/половина/1; память
  25–75% свободной. Кнопки «Старт», «Стоп» (останавливает сразу),
  «Очистить»; таймер и прогресс-бар; живые графики загрузки CPU,
  температуры (ACPI/nvidia-smi) и частоты (`CallNtPowerInformation`);
  скорость каждой нагрузки в сравнении с базовой (медиана первых
  секунд) — просадка ниже 80% фиксируется как троттлинг; журнал событий.
  Вердикт: температура выше `maxTempC`, падение скорости (`throttleMinPct`,
  `throttleMaxSharePct`), ошибки памяти/диска, температурная защита
  (остановка при `maxTempC` три секунды подряд). Защита от обрыва: при
  старте пишется `%LOCALAPPDATA%\Echips\HardwareCheck\stress_running.json`;
  если Windows перезагрузилась или зависла посреди теста, при следующем
  запуске приложение покажет последние показания и предложит записать
  «не пройден». По умолчанию в автопрогон не входит (добавляется в
  `tests` профиля; виды нагрузки — `stressStressors`).
- **Установка драйверов**: тот же каталог (Яндекс.Диск, публичная ссылка
  `MANIFEST_PUBLIC_URL` — тот же URL, что в `echips-driver-assistant`),
  тот же каскад подбора пакета (по модели → по префиксу серийника),
  скачивание, распаковка, `pnputil /add-driver ... /install`, создание
  точки восстановления, подробный лог в `%LOCALAPPDATA%\Echips\HardwareCheck\logs`.
  Работает на **любом** ноутбуке, не только Echips: если модель не найдена
  автоматически, открывается полный список моделей с поиском (найденная —
  сверху с пометкой), а при отсутствии модели — «Универсальный набор» по
  категориям (Wi-Fi, звук, Bluetooth и т. д.), где подсвечены категории,
  соответствующие устройствам с ошибкой драйвера. Прогресс по каждому
  файлу, список установленных пакетов, уведомление по завершении.
  **Права администратора**: `build.rs` встраивает манифест
  `requireAdministrator` (без него `pnputil` не устанавливает драйверы) и
  зависимость Common Controls 6 (без неё WebView2 падает при старте).
- **Замена платы — чтение**: реальное чтение текущих SN/UUID платы
  (`Win32_BIOS.SerialNumber`, `Win32_ComputerSystemProduct.UUID`) и
  тамперпруф-аудит-лог (SHA-256 хэш-цепочка, каждая запись ссылается на
  хэш предыдущей) в `%LOCALAPPDATA%\Echips\HardwareCheck\motherboard_audit.log`.
- **Отчёт**: экспорт в `.txt` (акт для клиента/для печати) и `.json`
  (для базы) в `%APPDATA%\ru.echips.hardware-check\reports`.
- **Вход по PIN при запуске**: список инженеров и хэшей PIN —
  `data/techs.json` в этом репозитории (публичный, только
  `SHA-256(salt+":"+pin)`, см. `src-tauri/src/commands/techs.rs`),
  подтягивается заново при каждом старте (с локальным кэшем на случай
  отсутствия сети). Определившийся инженер подставляется в поле
  «Инженер» отчёта и в аудит-лог замены платы автоматически — отдельный
  PIN-шаг там убран. Добавление нового инженера — экран "+ добавить
  инженера" в сайдбаре (считает `pin_hash` через Web Crypto прямо в
  приложении, готовую запись нужно вручную вставить в `data/techs.json`
  и запушить — без пересборки и релиза).

## Что оформлено как ручная проверка (по дизайну, не баг)

Клавиатура, дисплей, тачпад — сами экраны и вёрстка есть, техник проверяет
глазами/руками и отмечает результат. Это не автоматизируется без физического
взаимодействия, так и было задумано в прототипе.

## ⚠️ Требует вашего внимания перед использованием на реальном железе

1. **Запись SN/UUID (замена платы) — НЕ реализована, это осознанная
   заглушка.** `write_smbios_identity` в `commands/motherboard.rs` валидирует
   форму нового SN/UUID, читает текущие значения, пишет попытку в
   аудит-лог со статусом `"stub_not_written"` — но не вызывает
   AMIDEWINx64.exe и не переписывает SMBIOS. Причина: единственные
   command-line флаги AMIDEWINx64.exe, которые нашлись в открытом
   доступе, — с форумов про обход HWID-банов в играх, а не из
   официальной документации AMI. Подставлять их "как есть" для операции,
   необратимо переписывающей плату реального ноутбука, — слишком большой
   риск. **Нужно**: взять точный путь к `AMIDEWINx64.exe` и его аргументы
   из вашей текущей проверенной процедуры (раз она уже используется в
   сервисе) и подставить в эту функцию, прежде чем включать кнопку в
   продакшене. Если такой процедуры пока нет — стоит сначала
   свериться с официальной документацией AMI или с поставщиком платы.
   В `sn_write.rs` в исходном `diag/README.txt` упоминался готовый модуль
   для этого — но в актуальном публичном репозитории
   `echips-driver-assistant` такого модуля нет (только логика установки
   драйверов), так что этот кусок пришлось спроектировать с нуля, а не
   портировать.
2. ~~PIN-коды техников захардкожены в открытом виде~~ — сделано: общий
   экран входа при запуске (`data/techs.json` в публичном репозитории,
   только `SHA-256(salt+":"+pin)`, см. `src-tauri/src/commands/techs.rs`).
   Список подтягивается заново при каждом старте программы — новый
   инженер или изменённый PIN появляется на всех станциях без обновления
   .exe. Добавление инженера — через встроенный экран "+ добавить
   инженера" (генерирует хэш прямо в приложении, Web Crypto), результат
   нужно вручную вставить в `data/techs.json` и запушить. Отдельный
   PIN-шаг во вкладке "Замена платы" убран — техник уже определён общим
   входом.
3. **Температура/обороты кулера** — честно помечено "недоступно" на
   большинстве потребительских ноутбуков (ACPI thermal zone через WMI
   либо не публикуется вендором, либо даёт одно фиксированное число).
   Для реального мониторинга нужна интеграция с LibreHardwareMonitor
   или HWInfo (доступ к SMBus/EC) — отдельная задача, не сделана.
4. **Bandwidth-тест USB-порта** (запись/чтение с контрольной суммой, как
   в прототипе) не реализован — список USB-устройств есть, но не тест
   пропускной способности конкретного физического порта: для этого
   нужно заранее знать, какое контрольное устройство воткнуто в тестовый
   порт, это специфика конкретного сервисного центра.
5. **GPU-стресс-тест и детекция throttling** не реализованы — throttling
   нельзя достоверно увидеть без надёжного чтения частот/температур,
   которых нет (см. п.3).

## Сборка

Собирается только на Windows (или через CI) — код использует
Windows-специфичные WMI/PowerShell/`pnputil`/`powercfg` вызовы, обёрнутые в
`#[cfg(target_os = "windows")]`. `cargo check`/`cargo build` на macOS/Linux
не проходит из-за отсутствия системных библиотек GTK/WebKit для линковки
Tauri (это ожидаемо, не специфично для этого проекта) — используйте
GitHub Actions (`.github/workflows/build.yml`, ручной запуск через
"Run workflow" или пуш тега `v*`).

CPU/GPU, обороты вентиляторов, напряжения и мощность на вкладке «Датчики»,
в стресс-тесте и в тесте «Датчики».

0.5.0 — журнал сбоев (склейка записей, справочник ~70 кодов, диагноз по
шаблону, аппаратные события), активация Windows с пошаговым устранением,
стресс-тест как в AIDA64 (CPU/FPU/кэш/память/диск/GPU, Стоп, таймер, живые
графики, троттлинг, температурная защита, маркер обрыва).

0.4.0 — быстродействие (команды вне главного потока, постоянный PowerShell,
таймауты, кэш, perf.log), отчёт с подробностями и причиной смены вердикта,
кнопка «Развернуть» и F11, клавиатура (NumPad, счётчики, дребезг,
залипание), SMART: системный диск по умолчанию и порог CRC, память 4 ГБ × 4.

0.3.3 — исправлена вёрстка тестов (прокрутка, таблица SMART, графики), компактный
баннер автопрогона; стресс-тест убран из автопрогона по умолчанию.

0.3.2 — вкладка «Диск» с подвкладками: SMART (SATA и NVMe), сканирование
поверхности с графиком в реальном времени, тест записи до 100 ГБ; в
автопрогоне чтение/запись диска, память, датчики и стресс-тест.

0.3.1 — исправления по тесту на ПК: ложные ошибки USB, отпечаток, журнал
сбоев (одиночные отключения не ошибка), GPU NVIDIA в датчиках.

0.3.0 — профили моделей и автопрогон, сводка железа, диск (здоровье и чтение),
журнал сбоев, тест памяти, LAN, USB-накопитель, яркость, внешний монитор,
сигнал Wi-Fi, паттерны матрицы, запись камеры; исправления клавиатуры,
заливки на весь экран и экрана звука.

0.2.1 — установка драйверов на любых ноутбуках (ручной выбор модели,
универсальный набор, права администратора), логотип/иконки/шрифты/анимации
из Driver Assistant.

0.2.0 — интеграция реального дизайна (`diag.zip`), реальный бэкенд взамен
симулированных данных, экраны установки драйверов и замены платы.
